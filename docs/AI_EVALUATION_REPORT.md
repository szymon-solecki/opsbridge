# Operations Copilot evaluation

## Method

The evaluation runner creates a disposable PostgreSQL 17 database, verifies `opsbridge_test`, applies the existing migrations and persists synthetic scenarios with real OpsBridge tables and constraints. Reconciliation fixture reports are generated by the deterministic matcher. Stable fixture UUIDs and a fixed UTC clock make evidence identities and expectations repeatable. The runner calls the same request resolver, read-only evidence service and provider-response validator as the API. Question cases use the supported question grammar. Incident and reconciliation cases use the same structured targets as the dashboard; the catalog records the operator's question as evaluation intent rather than sending it to the provider.

The catalog at `scripts/copilot_eval/cases.json` ties facts to fixture aliases, expected evidence kinds, and fact fragments. Aliases resolve to actual record IDs and timestamps. The rubric distinguishes facts absent from the retrieved evidence from available facts omitted from the answer's selected references. It checks citation identity and timestamp, locally assembled summaries, allowed hypotheses and follow-up actions, uncertainty strings, and case-specific unsupported conclusions. Follow-up relevance means an approved action is paired with an expected hypothesis for the case. These rules test specific claims and structural contracts. They do not score general semantic quality, expressiveness, relative importance between optional facts, or uncatalogued paraphrases. Findings are exposed per case rather than collapsed into a single quality score.

## Remediation results

The rerun used the original catalog, requirements and grading code. Cases without rubric findings increased from **11 of 15 to 15 of 15**. Both runs completed every case with zero execution errors, citation violations, unsupported-hypothesis findings and unsupported-phrase matches. The remediated run also had zero missing or unselected expected facts. These results apply to deterministic offline behavior and the original synthetic rubric.

| Prior finding | Root cause | Evidence retrieved or selected after remediation |
| --- | --- | --- |
| Incorrect checksum | Delivery history read files and delivery events. Intake can quarantine a package before either record exists. | The finalized `INTEGRITY_MISMATCH` intake claim, cited at its finalization time. The error covers size or checksum verification, so the fact leaves the two possibilities open. |
| Duplicate source delivery | Repeat uploads reuse the accepted file and deliberately produce no additional receipt event. | Accepted claims scoped to the delivery and sharing the same stored file. Each claim has its own citation. The wording describes shared-file evidence without assigning which claim wrote the file. A quarantined `SOURCE_DELIVERY_ID_CONFLICT` is exposed separately, and a type-based failure lookup can find either quarantined outcome. |
| Corrected reconciliation and rerun | The query fetched only the selected run. | The selected `EXACT` summary and its immediate predecessor's `AMOUNT_MISMATCH` summary, each with its own run ID and timestamp. Historical classifications are labeled and do not drive hypotheses about the selected run. A single-group investigation stays scoped to that group and current run. |
| Retry exhaustion | The mock prioritized only the first three hypothesis citations. Those covered the file and the two newest attempt events. The remaining first attempt ranked behind surrounding context. | The mock independently prioritizes operational records as observations while preserving the anchor and the existing citation cap. It selects attempts 3, 2 and 1 in their persisted history order. |

Intake evidence is capped at four finalized, relevant claims, ordered by finalization time and claim ID. In a before-acknowledgement investigation, the cutoff applies to both claims used to establish a duplicate. The predecessor lookup reads one parent by ID and projects only status, attempts, timestamps and allowlisted result counts. Structured evidence remains sanitized and the evidence transaction remains read-only.

| PostgreSQL evidence retrieval | 18.747 / 34.790 / 34.790 ms | 22.411 / 43.734 / 43.734 ms |

The measured retrieval median increased by 3.664 ms and p95 by 8.944 ms. Retrieval includes the additional bounded reads. These are small local samples and p95 and p99 are the same sample maximum. An earlier remediated run also passed 15 of 15 scenarios with a retrieval p95 of 56.223 ms, indicating run-to-run variability. The final run recorded zero provider attempts and is saved locally as `data/performance/copilot-evaluation-remediated-final.json`.

The remediated image passed 226 backend tests, including three added tests for intake evidence and acknowledgement cutoffs, parent-run citations, and retry selection. The isolated recovery harness and all 11 Chromium cases passed, as did nine evaluator tests, the backend and frontend production builds, quiet Compose validation and whitespace checks.

## Security results

Six cases persist synthetic adversarial strings across integration names, filenames, error messages, event fields, operator comments, notification owners and an unknown event type. The runner audits each provider input for these sentinels, original UUIDs, synthetic source values, amounts, filenames and a synthetic email address. Analysis and citation validation retain record IDs locally. The outbound adapter exposes normalized observations, timestamps, temporary evidence labels and allowlisted investigation paths. It exposes no tool invocations. The tests also exercise unsupported SQL, incident-action, reconciliation-trigger and private-file requests. The existing PostgreSQL regression verifies that an attempted write in evidence retrieval fails with SQLSTATE `25006`. A synthetic HTTP transport tests failures and retries, structured output, forged citations, token reporting and partial cost calculation without calling OpenAI.

No adversarial text appeared in the generated summary, selected facts or suggestions in the offline run. Free text that the application retains locally as display labels remains untrusted. The implementation's fixed query grammar, read-only transaction and validated selection prevent an external provider from invoking actions. These tests cover the catalog and the application boundaries; they do not establish immunity against all prompt injection or substitute for privacy approval.

## Reproduce offline

Run from the repository root using an existing local Docker Desktop Linux engine. The launcher mounts only evaluation code and migrations, publishes no ports, uses a private network namespace without egress, and removes the disposable database container at exit. It requires cached images and never imports local `.env` or database settings.

```powershell
docker build -t opsbridge-backend:intake-check backend
docker pull postgres:17
.\.venv\Scripts\python.exe scripts/evaluate_copilot.py
docker run --rm --network none -e PYTHON_DOTENV_DISABLED=1 --mount "type=bind,source=$PWD/scripts/copilot_eval,target=/app/copilot_eval,readonly" --entrypoint python opsbridge-backend:intake-check -m pytest copilot_eval/test_runner.py -q -p no:cacheprovider
```

Save stdout as JSON for repeated comparisons. `--case NAME` selects a case and can be repeated. `--limit` bounds the number of cases and `--concurrency` accepts one to four. An execution error, privacy violation or invalid citation fails the run. The known retrieval and selection findings remain visible without causing an execution failure.

## Explicitly authorized live evaluation

**Live status:** unexecuted. There are no real model quality results, request latency measurements, token counts or charges in this report. The simulated transport tests establish adapter behavior only.

Obtain explicit authorization for the selected model and maximum spend before invoking live mode. Use a restricted project API key with access to the Responses API, an approved model ID that supports strict structured output, and that model's current uncached input and output token prices and context limit. Provide the key through a secret manager or the masked process prompt in a dedicated PowerShell session. The key stays outside the repository and is forwarded by environment variable name only to the disposable live runner. A local Docker administrator can inspect container environment values while it runs. Use a trusted local Docker engine and a restricted key. The live evaluator opens egress only when `--live` is supplied; PostgreSQL still listens on namespace loopback. The adapter sends requests to `https://api.openai.com/v1/responses` with `store: false`. The application deployment provider configuration is independent of this evaluator.

The following interactive invocation is for **one explicitly authorized case**. Enter the approved model, spending limit and current price values when prompted. The reserve assumes all allowed attempts use the configured model's full context as input plus up to 350 output tokens per attempt. The launcher refuses runs whose reserve or worst-case request count exceeds the supplied limits. This is a local estimate based on operator-supplied prices and context size. It does not enforce a provider-side billing limit. Restrict provider project access and review provider billing independently.

```powershell
$model = Read-Host 'Approved model ID'
$context = Read-Host 'Published model context limit in tokens'
$inputPrice = Read-Host 'Uncached input price in USD per million tokens'
$outputPrice = Read-Host 'Output price in USD per million tokens'
$budget = Read-Host 'Approved total USD spending limit'
try {
    $env:OPENAI_API_KEY = Read-Host 'OpenAI project API key' -MaskInput
    .\.venv\Scripts\python.exe scripts/evaluate_copilot.py --live --model $model --model-context-tokens $context --input-usd-per-million $inputPrice --output-usd-per-million $outputPrice --spend-limit-usd $budget --max-requests 2 --limit 1 --case invalid-csv --concurrency 1 --timeout 11
} finally {
    Remove-Item Env:OPENAI_API_KEY -ErrorAction SilentlyContinue
}
```

The live runner reports per-attempt HTTP status, elapsed time and safe failure code. The adapter makes at most two attempts within the case deadline. It retries transient failures only. Per-case and aggregate metrics include reported input, output and total tokens, the number of attempts with usage, and the estimated cost for attempts with both billing inputs. Attempt history also exposes retries. Missing usage remains unknown, including when a timed-out request may have reached the provider. Configured standard input/output rates do not model cache discounts, taxes or additional provider billing rules.

## Follow-up decisions

Keep the distinction between retrieval and ranking if the catalog grows. A real-provider comparison requires a separately approved budget and a manual review of borderline relevance and uncertainty outcomes. The present catalog covers one-hop reconciliation lineage and finalized intake evidence within a short history. It does not establish behavior for long histories, all vendor failure types, or a real model.
